# Programme Architecture

## Use this reference when

Use this reference to turn a brief into a linked learning programme. Use MDP Architect when the output needs both a programme spine and two or more connected session surfaces. Hand a raw source request to `mdp-source-finder`, a one off keynote or script to `teaching-designer`, and a standalone worksheet to `worksheet-generator`.

## Build the spine before any chapter

1. Read the current teaching workspace rules, the programme README, its source ledger, the approved Programme Thesis Record, the approved Book Foundation Record when the programme is book-shaped, and the latest rendered artifact.
2. Start from the promised learner change and the evidence that would make that change observable. Do not start from a list of concepts to cover.
3. Write one programme question. It must describe the capability the room will build, not the topic it will hear about.
4. Name the carried participant artifact or observable performance. It must gain one usable layer in each session and provide evidence for the programme promise.
5. Sequence sessions as a decision journey: disturbance, map, mechanism, test, redesign, commitment. Use different moves when the subject requires them; do not force these labels into the visible programme.
6. Give each session one question that makes the next session necessary and one capability move whose proof survives the room.
7. Build the official timetable separately from the facilitation capacity. Do not silently change client times to fit a richer design.

## Audit inheritance before redesigning it

When an outline, syllabus, curriculum, or earlier edition exists, map it before writing the replacement. This is not a preservation quota. The audit lets the architect retain a necessary function without mistaking its inherited form for the only way to perform it.

For every source item being considered, record:

| Field | Question |
| --- | --- |
| Source concept or question | What exactly is inherited? |
| Original purpose | What learner or organisational need was it meant to serve? |
| Enduring requirement | Does that need still exist? If not, say so. |
| Inherited form | How was the need previously taught or handled? |
| Changed condition | What is now different in the work, environment, learner, or evidence? |
| Author claim or synthesis | What does the author now argue, beyond summarising sources? |
| Disposition and reason | Preserve, reframe, combine, resequence, add, or omit—and why? |
| Programme fit and destination | Where, if anywhere, does it belong in the new journey? |
| Evidence status | Established external, author experience/teaching observation, author synthesis, or open hypothesis. |
| Learner move and proof | What will the participant do, and what artifact state or performance shows it? |

Classify the enduring-requirement/changing-form lens for the whole programme as `Central`, `Supporting`, or `Not applicable`, and state why. `Not applicable` is not a failure. A greenfield product-thinking programme may have no inherited form to preserve; a non-AI leadership programme may have no changed technology mechanism to diagnose. Do not manufacture either one.

When AI materially changes the subject, name the changed mechanism precisely: representation, prediction, coordination, execution, monitoring, memory, or agency. More than one may apply, but each must produce a traceable change in the learner's decision or artifact. Generic AI vocabulary does not count as a changed condition.

## Required programme plan table

Place the programme plan table immediately after the cover in a programme-review HTML artifact. In a public-book artifact, use the placement approved in the Book Foundation Record: it may appear in the interactive shell, as a reader-facing roadmap, or remain out of the Book reading flow. Do not expose an internal timetable merely because the source began as a course. Each row must contain:

| Field | Requirement |
| --- | --- |
| Session | Number, title, official duration, and position in the journey. |
| Central question | One question with a practical decision at stake. |
| Entry problem or consequential task | The disturbance, decision, interpretation, diagnosis, craft task, or demonstration that opens the session. |
| Capability move and proof | What the participant becomes able to do, plus the artifact state or performance that makes the move observable. |
| Carried artifact | The exact participant output that enters or leaves the session. |
| Core mechanism | One framework, map, or test that earns its place in the case. |
| Commitment | What participants choose, interpret, diagnose, attempt, or construct before any reveal, challenge, or worked comparison. |
| Handoff | The unresolved question and artifact version that the next session receives. |

Do not use the table as a catalogue. A reader should see why Session 4 could not happen before Session 2 and how the final artifact proves the promise made at the start.

## Session design rules

Each session must contain one sustained object of attention, stored under the
canonical `case` type. It may be an event, decision, text, specimen, dataset,
diagnosis, performance, or craft attempt. Give it a concrete choice,
interpretation, diagnosis, or move; the consequence or quality at stake; a
constraint; and something the learner cannot yet know, see, or do. Use typed
actors from the session registry for the people or agents involved, including
the learner role in a practice case. Bind every actor to the block where the
role first appears so responsibility cannot materialise only when it becomes
convenient. Return to the sustained object at decisive moments rather than
through a mechanical callback quota. Permit one to three bounded lateral
examples when each clarifies a different move the main case cannot show. Every
example must return to the question or task it was chosen to explain.

Audit the case portfolio across the full programme. Vary domain, geography,
medium, actor, object, task scale, and evidence form when that variety helps the
argument; do not make every chapter another manager meeting or another HR
exception. Diversity is diagnostic rather than a quota: a repeated case is
justified when continuity produces more learning than novelty, and a new case
is justified only when it performs work the existing case cannot.

Build the protected core to the official session duration. Add prepared runway according to the brief and author profile; do not hide that extra capacity inside the client timetable. In Shiva's current teaching profile, a 90-minute session normally carries 30 minutes of named depth reserves. Another author or programme may set a different runway deliberately. Every core segment names a facilitator move, participant move, artifact state, and recovery move. Every reserve deepens the existing case, mechanism, or artifact and names its trigger, participant move, and rejoin state.

Use this timing ledger for every session:

| Lane | Must show |
| --- | --- |
| Core, official duration | Required moves, their timing, facilitator move, participant move, artifact state, and recovery move. |
| Prepared runway | Trigger for use, added move, participant move, minutes, artifact state, and an explicit rejoin line. |
| Official timetable | Client committed start, end, and break details. Keep it separate from the capacity ledger. |

## Architecture completion check

Do not draft a chapter until the Programme Thesis Record is approved for the requested scope, inherited material has a disposition where applicable, and all sessions have a central question, capability move, observable proof, carried artifact, commitment point, source need, and handoff. Reject a programme that has topic labels but no artifact progression, sessions that can be reordered without changing the learner's work, or a promise that no session artifact can substantiate.
